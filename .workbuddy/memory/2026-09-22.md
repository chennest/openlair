## 排错：PVE 宿主启动进 emergency mode（fstab 挂载项设备缺失）

超哥发来控制台截图求助，最终已恢复正常。

### 现象（截图）
```
Timed out waiting for device dev-disk-by\x2duuid-ccd516dc\x2e.device
[DEPEND] Dependency failed for mnt-sata256g.mount - /mnt/sata256g.
[DEPEND] Dependency failed for local-fs.target - Local File Systems.
[DEPEND] Dependency failed for systemd-fsck@dev-disk-by\x2duuid-ccd516dc...
You are in emergency mode...
```

### 定位结论
- **与 ceph 无关**：`ceph-d55d9207…`/`ceph-7f179629…`/`ceph-288bcb80…`/`pve` 四个 VG 均正常 Found 且各 1 个 LV，`/sbin/fsck.xfs: XFS file system.` 也只是正常输出。
- **根因**：`/etc/fstab` 中 `UUID=ccd516dc-…  /mnt/sata256g` 指向的块设备开机时不存在 → systemd 等满默认 90s 设备超时 → `mnt-sata256g.mount` 失败 → `local-fs.target` 失败 → 进 emergency mode。典型的「单块非关键数据盘掉线拖死整机启动」。

### 给出的处置路径
- rescue shell：`mount -o remount,rw /` → `blkid | grep -i ccd516dc` → `lsblk -f` → `journalctl -xb | grep -B5 -A20 ccd516dc`
- 三分支判因：① 盘物理掉线（`lsblk` 无盘 + `dmesg | grep -Ei 'ata|sata|scsi|error'`）② 盘在但 UUID 变更（`blkid` 对不上）③ 设备实为 LV 而所在 VG 未激活（`pvs/vgs/lvs`）
- 永久修复：UUID 变更则改 fstab；盘不再需要则注释该行；非关键盘加 `nofail,x-systemd.device-timeout=10` 防复发。
- ⚠️ **红线**：确认盘归属前禁止格式化/重建分区表，防误伤 ceph OSD 的 wal/db 设备；恢复后查 `ceph -s`、`ceph-volume lvm list` 看 OSD 是否 flapping。

### 事后 ssh pve02（192.168.6.7）实查确认
- **256G 盘确实不在系统里**：`lsblk` 只有 `sda`（119.2G INTEL SSDSC2KF128G8L，PVE 系统盘）+ 三块 NVMe —— `nvme0n1` 953.9G / `nvme1n1` 476.9G / `nvme2n1` 1.8T，**全部被 ceph OSD 的 `ceph_bluestore` LV 占满**。`blkid | grep ccd516dc` 无输出。→ 不是 UUID 变更，是盘缺失。
- `/etc/fstab` 第 6 行已被注释：`#UUID=ccd516dc-7d14-4d9e-a62b-93e3875def63 /mnt/sata256g ext4 defaults,noatime 0 2`，`/mnt/sata256g` 当前未挂载（df 只有 `pve-root`）。这就是恢复的原因。
- dmesg 无 ATA/SCSI I/O error；`sdb~sdi` 那 8 个 "SCSI removable disk" 是 USB 读卡器的多 LUN，非故障。
- 主机：pve02，pve-manager 9.1.5，kernel 7.0.14-17-pve；ceph mon/mgr/mds 均为单节点自持。

### 新发现：`k8s-rbd` 池 CRUSH 规则配错（HEALTH_WARN 的真正根因）
- `k8s-rbd`（pool 6，size 2 / min_size 1）用的是 **crush_rule 0 = `replicated_rule`**，failure domain = **host**；而集群只有 **1 个 host（pve02）** → 第 2 份副本无处安放 → **64 个 PG 全部 `active+undersized+degraded`**，健康摘要里的 0.5% degraded / 64 pgs undersized 全出自这一个池。
- 对照组：`vm_storage`(2) / `cephfs_data`(4) / `cephfs_metadata`(5) 同样 size=2，但用的是 **crush_rule 1 = `same-host`**（`choose_firstn type osd`，failure domain = **osd**）→ 268 PG 全部 active+clean。
- `single_storage`(3) size=1 + rule 0、`.mgr`(1) size=1，size=1 不受影响。
- **修复**：`ceph osd pool set k8s-rbd crush_rule same-host` → 触发 backfill 补齐第 2 副本。该池仅 2.0 GiB / 1.31k 对象，迁移很快，且可随时设回 rule 0 回滚。
- 沉淀的硬约束：**单节点 Ceph 里 size>1 的池必须挂在 osd 级故障域规则上**，默认 `replicated_rule`（host 域）在单 host 下永远 undersized。
- 次要 WARN：64 pgs not (deep-)scrubbed in time，是同一批 PG，变 clean 后会自动补 scrub。

## 调研：JuiceFS 的 4K 随机 IO 性能（超哥问「juniefs 的 4k 性能搞不搞」）

**结论：4K 性能不由 JuiceFS 本身决定，由数据命中哪一层决定，跨 4 个数量级。**

### 分层实测（4K 随机读，官方/DZone 数据）
| 层级 | IOPS | 延迟 |
|---|---|---|
| 穿透对象存储（同步 4K） | **25** | 30–55 ms |
| 穿透对象存储（libaio qd64） | 1,530 | — |
| 分布式缓存（同步 4K） | 6,893 | 0.1–0.2 ms |
| 本地缓存（同步 4K） | 14,700 | 0.05–0.1 ms |
| 本地缓存（libaio qd64） | 30,800 | — |
| 本地缓存（qd64 ×4 并发） | 116,000 | — |

### 官方 benchmark（32C/64G/40Gbps，分布式缓存供数）
- 4K randread 单进程 iodepth=8 峰值 **68K IOPS**；多进程 numjobs=12 → **258K IOPS**，延迟 ~0.4ms。
- 对照 GPFS：iodepth=16 达 83K；numjobs=12 读不同文件 433K（读同一文件因锁竞争 numjobs>2 后下滑）。
- 4K 随机写依赖 **writeback**：cache-dir 设本地 NVMe 时 numjobs 1→3 从 28K→56K IOPS；不开 writeback 直接被后端对象存储卡住。

### 途虎生产实测（JuiceFS + Ceph RADOS，关本地缓存）
- 4K 随机读 **77,984 IOPS** / 3,394 MiB/s；4K 随机写 **3,836 IOPS** / 4,120 MiB/s（MinIO 后端随机写仅 1,194 IOPS）。
- 小文件写 817 files/s（vs MinIO 147.2，**5.5×**）；小文件读 3,776 files/s（3.2×）。
- 原因：librados 直连 RADOS，比 RGW(S3) 少一层网关转发。

### 选型判断规则
- 数据集 < 缓存容量 / 有热点（AI 训练数据、模型加载、镜像层、日志）→ ✅ 能搞，接近本地盘。
- 持续 4K 随机读且数据集远大于缓存 → ❌ 别搞，落到 25–1,530 IOPS 级别。
- 数据库 / VM 镜像（fsync 敏感）→ ⚠️ 谨慎，writeback 牺牲一致性语义（数据先落本地缓存异步上传）。
- 元数据/小文件 ops → ✅ Redis 元数据引擎足够快，远胜 NFS。

### 给 pve02 场景的建议
- 后端优先 **RADOS（librados）而非 RGW/S3**；元数据引擎上 Redis；客户端 `cache-dir` 挂本地 NVMe。
- 注意单节点 Ceph 只有 3 OSD、无并行优势，后端 4K 底子有限；JuiceFS 的价值在于把 Ceph 包成多 Pod 共享文件系统。

### 避坑
- 网传「4K randrw iodepth=64 → 285K IOPS」是**缓存命中**数据，不能作容量规划依据。判断标准永远是命中率。

## 调研：JuiceFS 各厂商落地模式（超哥问「分享的这个案例咋落地的，各大厂商」）

### 收敛后的参考架构（各家高度一致）
应用（训练框架 / 推理服务 / Spark·Hive / Notebook）→ 接入（POSIX · HDFS API · S3 网关 · K8s CSI / Fluid）→ JuiceFS 客户端（本地 NVMe 缓存 L1）→ 控制流走元数据引擎、数据流经分布式缓存集群 L2（一致性哈希）→ 对象存储后端（OSS/COS/TOS/S3/Ceph RADOS）。

### 云厂商（做平台 / 做服务）
- **腾讯云**：JuiceFS + FoundationDB 企业级统一存储平台。**无状态元数据服务 + ZooKeeper**（服务注册/发现/状态同步），客户端走 RPC 不再直连 FDB；FoundationDB 7.3 triple 三副本 + SSD，单卷支撑 **108 亿**元数据。两种模式：托管模式（chunk/slice/block 写对象存储）+ 外部模式（UFS 抽象层，不迁数据，fingerprint 保证一致性）。两级缓存 L1 本地 + L2 自研独立缓存集群，支持预热/防击穿/TTL 驱逐/透明降级。Agent Runtime 用 Sidecar 模式挂载。
- **火山引擎（字节）边缘渲染**：选型历程 = 内部存储组件（IDC 导向、机器规格要求高）→ **CephFS + MinIO**（1000 万文件后性能退化、偶发卡顿）→ JuiceFS。**元数据用 MySQL**（单实例 / 一主二从，MySQL Operator orchestrator 做同步，高性能云盘由 Ceph 提供作数据盘），理由：千万级文件 + 读多写少场景下 MySQL 运维/可靠性/事务更优。K8s **DaemonSet 挂载 + HostPath** 给渲染 Pod；LDAP 认证；S3 网关 + POSIX 统一（替换原来 TOS 上传→下载→渲染→回传的多次拷贝）。开缓存吞吐提升 3–5 倍。日志服务 TLS 做可观测。

### 五个血泪坑（实战价值最高）
1. **知乎**：Redis 单线程 + JuiceFS 对 >6.4GB 文件的 scan 操作，被 PyTorch 增量写 zip_file 触发的 truncate 激发 → **setattr 耗时 577 秒** → CPU 打满、集群不可用。
2. **理想汽车**：托管 Redis 单实例扩容瓶颈限制文件总数 → 转 TiKV。（⚠️ 该文「因需要事务 API 无法使用集群模式」的表述不准，已在下文补正 —— 官方 v1.0.0+ 支持 Redis Cluster，但 hash tag 会把单卷锁死在单节点，用了也白用。）
3. **阶跃星辰**：激进预读调优把单节点拉到 100+GB/s → 读线程过多导致缓存组节点失联、**缓存雪崩** → 结论「存储性能不必追求极致，不成为瓶颈即可」。
4. **火山引擎**：CephFS + MinIO 在 1000 万文件量级性能退化 + 偶发卡顿。
5. **九识智能**：Ceph 扩 OSD 与 rebalance 耗时、小文件写性能差。

### 提炼的规律
- **元数据引擎演进路线**：Redis（起步，受单实例限制）→ MySQL（千万级，运维友好）→ TiKV（十亿级）→ FoundationDB（百亿级）→ 企业版自研（千亿级 + 亚毫秒）。
- **缓存模式统一**：L1 本地 NVMe + L2 分布式缓存集群（一致性哈希路由）+ 预热编排（Fluid DataLoad / 自研 API）。
- **跨云统一命名空间靠「镜像文件系统」**：主 FS 在中心，边缘部署镜像，元数据自动复制，边缘不存数据只预热缓存。
- **自建场景后端**：Ceph RADOS（librados）明显优于 RGW/S3 网关（途虎实证）。

## 补正：JuiceFS 对 Redis Cluster 的支持真相（超哥追问「redis cluster 也可以这样吧」）

- ⚠️ **官方确实支持 Redis Cluster**（v1.0.0+），并非"不支持"。META-URL：`redis[s]://[user:pwd@]addr:port,addr:port,addr:port[/DB]`。
- **机制**：靠 Redis **Hash Tag** —— JuiceFS 给所有 key 加 `{DB}` 前缀（如 `{1}`），把同一文件系统的全部 key 锁进**同一个 slot**。官方中文原话：「为了避免在 Redis 集群中执行跨节点事务，**同一个文件系统的元数据总会坐落于单个 Redis 实例中**」。
- **代价**：分片只到「卷级」—— 一个卷 = 一个节点，**单卷变大只能纵向扩容**。官方 blog 原话："if there is one file system that is particularly large, scaling can only be done through vertical scaling"。
- → 所以「因需要事务 API 无法使用集群模式」表述不准，实质是**用了 Cluster 也白用**，单卷仍被锁单节点。上一条引用该说法未查证，此处更正。
- **容量公式**：每个文件元数据约占 **300 字节内存** → 1 亿文件 ≈ **30 GiB** 内存。用 `INFO memory` 的 `used_memory_dataset` 核对（不含 `used_memory_overhead`）。必须设 `maxmemory-policy noeviction`，否则元数据可能被驱逐。
- **Redis 系（含 Cluster）治不好的两点**：① 主从**异步复制**，必然可能丢元数据（丢元数据 = 文件系统损坏）；② 全内存成本高。官方建议改用带强一致的 Redis 兼容服务：阿里云 Tair、华为 GaussDB for Redis、AWS MemoryDB。
- 其他要点：`route-read=replica`（v1.0.0+，只读挂载走副本降低 master 负载）；Valkey 与 Redis 在使用上完全等价。
- **核心结论**：Redis Cluster 解决的是「多卷共用一个集群」的运维成本，**不是「单个大卷怎么扩容」的容量问题**。要单卷横向扩，只有 TiKV / FoundationDB / 企业版自研这类真分布式事务引擎。

## 补充：元数据容量公式 + 社区真实规模（官方来源）

- **容量公式**（官方文档）：键值库（Redis/TiKV）**300 字节/文件**；关系型（SQLite/MySQL/PG）**600 字节/文件**。
  放大因素：平均文件 >64MB、频繁修改产生碎片、扩展属性多、平均文件名 >50 字节。
  迁移换算例：MySQL 用量 30GB → 目标 Redis 至少备 15GB 内存。
  **实测反推系数**：按官方文档示例（`used_memory_dataset` 13.44GB ≈ 4480 万文件，而 `used_memory_rss` 20.68GB）→ **RSS ≈ 文件数 × 462 B ≈ 数据集 × 1.54**（overhead 约占 30%）。
  **1 亿文件**：数据集 30GB → 实际 RSS **约 46GB** → 生产实例按 **64GB** 规格备（留 fork/COW 余量）；**主从架构内存直接翻倍到 128GB**。这正是社区「运行中 Redis 集群最大约 1.5 亿文件」的根本原因。
  自查命令：`redis-cli INFO memory | grep -E "used_memory(_dataset|_rss|_overhead)?:"`。

## 深挖：为什么是「300 字节/文件」（超哥追问「为啥要这样算、为啥这么多」）

### 第一层放大：一个文件 ≠ 一条 KV，而是 2~4 条
JuiceFS TKV 完整 key 表（源码 `pkg/meta/tkv.go`）：

```
setting                          format
C{name}                          counter (nextInode/nextChunk/nextSession)
A{8B-inode}I                     inode 属性（权限/时间/大小/nlink）
A{8B-inode}D{name}               dentry 目录项
A{8B-inode}P{8B-inode}           parents（硬链接）
A{8B-inode}C{4B-blockID}         file chunks（每 64MB chunk 一条）
A{8B-inode}S                     symlink target
A{8B-inode}X{name}               extended attribute
D{8B-inode}{8B-len}              deleted inodes
F{8B-inode} / P{8B-inode}        Flocks / POSIX locks
K{8B-sliceID}{8B-blockID}        slice refs（引用计数）
L{8B-sliceID}                    delayed slices
SE/SH/SI/SS{8B-sessionID}        session 相关
U{8B-inode}                      目录用量统计
N{8B-inode}                      detached inode
QD{8B-inode}                     目录配额
R{4B-aclID}                      POSIX acl
```

- **设计巧思**：全部用 `A` 前缀 + 8 字节 inode，使**同一 inode 的所有 key 前缀相同** → 落在同一 Region/slot，把事务尽量收敛到单节点（对应前面说的「第三个 key 要靠近前两个」）。
- 编码：inode/counter 用小端 8 字节；sessionID/sliceID/timestamp 用大端 8 字节。
- 普通文件最少 **2 条**（inode 属性 + dentry）；带数据再加 `C{blockID}`；每个 slice 再加 `K{sliceID}*`。

### 第二层放大：Redis 每条 KV 的固定开销 ≈ 88~112 字节
| 组成 | 字节 |
|---|---|
| dictEntry 结构 24B → jemalloc 分配 | **32B** |
| redisObject | **16B** |
| key SDS（4B 头 + 内容，jemalloc 取整） | ~16B |
| value SDS | ~16B |
| 哈希桶指针（桶数组 ≈ key 数 × 8B） | **8B** |

- ⚠️ **jemalloc size class 阶梯效应**：key/value 从 12 字节增到 13 字节，SDS 由 16 跳到 32 → **单条 dictEntry 直接从 80B 变 112B**。字符串长度微调 1 字节，内存可能翻倍。

### 结论算式
`2~4 条 × ~100 字节 ≈ 300 字节/文件`；关系型数据库多一层表索引 → `600 字节/文件`。

### 实践启示（重要）
**文件数本身就是元数据成本**，所以把小文件打包成大文件（tar / parquet / webdataset）能直接把元数据内存需求降一个数量级。阶跃星辰也提到：打包后的数据集面临高并发随机读，未打包则大量小文件直接冲击元数据性能。
- **社区真实规模**（官方 Medium 答疑）：
  - Redis 仍是社区第一大选择（一半以上），TiKV 与 MySQL 次之且在增长
  - **运行中的 Redis 集群最大文件数约 1.5 亿**，运行相对稳定；1 亿是推荐值而非硬上限
  - **TiKV 被文件总数排名前三的集群使用，均超 10 亿文件**；目前最大文件系统 **70+ 亿文件 / 15+ PiB**；官方内部实测 TiKV 存 **100 亿文件**
- **官方选型口径**：① **存关键数据的话 Redis 不合适**（会丢数据/短暂中断）；② 无论用哪个引擎都**基本需要高速 SSD**；③ 「**我们一般建议用户一开始选择自己熟悉的数据库**」；④ 元数据引擎迁移只能迁到空库。

## Tair（阿里云）与 Redis 的区别

- Tair 是**产品线**不是单品：`Redis 开源版` / `Tair（企业版）` / `Tair Serverless KV` 三类实例；企业版又分 **内存型 / 持久内存型 / 磁盘型（ESSD/SSD）**。
- 三形态官方数据：

  | 形态 | 性能（Redis 开源版=100%） | 成本 | 落盘一致性 | 持久化级别 |
  |---|---|---|---|---|
  | 内存型 | 300% | 117% | Write Back | 秒级 |
  | 持久内存型 | 90% | 70% | **Write Through** | **命令级** |
  | 磁盘型 | 读 40–60% / 写 30–40% | **15–20%** | **Write Through** | **命令级** |

- ⚠️ **关键勘误**：阿里云特性对比表中「**主备复制一致性**」一栏，**所有形态（含 Tair 全部形态与 Redis 开源版）都是「最终一致」**。真正变强的只是「落盘一致性」→ 持久内存型/磁盘型为 Write Through + 命令级持久化，解决「掉电丢数据」，但**主备切换仍有数据回退窗口**。「半同步模式」仅内存型与磁盘型(SSD)支持。
  → 上一条「官方建议用 Tair 提供强一致」表述过于笼统，应细化为「**持久化可靠性增强**」，主备同步语义未变。
- ⚠️ **对 JuiceFS 的两个风险点**：
  1. **Lua 脚本**：Tair 官方《开发运维规范》明确「推荐使用扩展数据结构，**避免使用 Lua 脚本**」「Lua 无法被多线程加速」。而 JuiceFS 元数据操作重度依赖 Lua（EVAL）→ **必须实测**；另有沙箱限制（KEYS、TIME、RANDOMKEY 等非确定性命令可能直接报错）。
  2. **CROSSSLOT + 倾斜**：Tair 集群版事务要求所有 key 在同一分片，JuiceFS 的 `{DB}` hash tag 正好满足，但官方规范也提醒「避免 hash tag 带来的存储倾斜」。
- 其他：Tair 支持 **256 个 DB**（0–255，默认 db0；Redis 开源版只有 16 个）；兼容 Redis 4.0/5.0/6.0/7.0。
