## CI 构建缓存诊断（.gitlab-ci.yml，仅分析未改动）

**结论：buildah 构建的镜像缓存 100% 不复用。**

- `backend-package` / `web-package` 两处 `buildah bud` 缺失三点：`--layers`（不写则 `--cache-from`/`--cache-to` 被官方文档明确忽略）、`--cache-from`、`--cache-to`。
- `STORAGE_DRIVER: vfs` + 容器内临时目录 → k8s executor 每个 Pod 都是空白 storage，本地层缓存天然不跨 pipeline。
- 修复方向（待超哥确认）：`buildah bud --layers --cache-from "$CACHE_REPO" --cache-to "$CACHE_REPO"`，缓存推独立 Harbor repo `chennest/openlair-backend-cache` / `openlair-web-cache`（避免污染业务 tag 列表）。

**附带发现 —— 光加 cache 不够（关键）：**
`lairweb/Dockerfile` Stage1 的 `ARG APP_VERSION` / `ARG APP_COMMIT` 声明 + 紧跟的 `ENV APP_VERSION=${APP_VERSION}` 位于 `pnpm install` **之前**，而 TAG 每 pipeline 都变（`test-<CI_PIPELINE_IID>`）→ 该层缓存键必变 → 之后所有层（corepack、COPY lock、pnpm install、pnpm build）永远 miss。需把 ARG/ENV 下移到 `COPY . .` 之后、`RUN pnpm run build` 之前（或只在 Stage2 注入）。

**次要：** `backend/Dockerfile` 里 `RUN --mount=type=cache,target=/root/.cache/uv` 在 k8s executor 下每次都是空 cache（cache mount 不落镜像层，Pod 销毁即失），CI 场景基本白挂；不过 uv sync 层命中后整个 RUN 不执行，影响可控。

**资料澄清：** buildah `--cache-from` registry 分发自 **v1.27.0（2022-08）** 实现，CI 用的 v1.37 支持；网上「buildah --cache-from 是 NOOP」的说法对应 <1.27，已过时（别被中文博客误导）。

## 落地改动（超哥确认后实施，未 commit）

改了 2 个文件：
- `.gitlab-ci.yml`：`backend-package` / `web-package` 各补 `--layers --cache-from --cache-to`；cache 仓库用独立 repo `openlair-backend-cache` / `openlair-web-cache`；新增一行剥 scheme 后拼 `CACHE_REPO`。
- `lairweb/Dockerfile`：`ARG/ENV APP_VERSION|APP_COMMIT` 从 Stage1 顶部**下移到 `COPY . .` 之后、`pnpm run build` 之前**（否则版本号变化会打断 pnpm install 层缓存）。

**从 buildah 官方文档 + 源码确认的关键点（已写进 CI 注释）：**
1. `--cache-from/--cache-to` 走 `parse.RepoNamesToNamedReferences` → **只接受裸仓库名**，带 `https://` 会解析报错。而本项目 `HARBOR_HOST` 是 `https://harbor.lcc007.top`，故用 `${HARBOR_HOST#*//}` + `${%/}` 剥掉 scheme（四种输入形态均已实测）。
2. cache tag = `<repo>:<sha256(cacheKey)>`（64 位 hex 内容哈希）→ 天然幂等，多流水线并发不覆盖，**不需要按分支/环境分 cache repo**。
3. cache 拉取失败**非致命**（源码 `logrus.Debugf` + `continue`，调用处 err 被显式忽略）→ 首次冷启动不会失败，也不需要 `|| true` 兜底。
4. `--layers` 默认 **false**，不写则 `--cache-from/--cache-to` 被直接忽略（官方文档明确）。

**待办 / 待验证：**
- Harbor 侧给 `openlair-backend-cache`、`openlair-web-cache` 两个 repo 配 tag 保留策略（cache tag 是 64 位 hex，量极大，会堆积）。
- 跑一次 test 分支 pipeline，日志里应出现 `Cache pulled from remote <repo>:<key>` / `Cache pushed to remote`。
- 潜在风险：`STORAGE_DRIVER: vfs` 无 CoW，开 `--layers` 后层间写放大会明显（每层整树复制）；若实测净收益不佳，后备方案是 runner 侧换 `fuse-overlayfs`，或挂 hostPath 持久化 storage 走纯本地缓存。
- 本机 Windows 无 buildah，改动属静态修改，行为需 CI 实测确认。

## 超哥补充口径（2026-09-23 22:06）

- **命名约定已确认**：buildah 分布式缓存的 cache repo 名 = **业务镜像名 + `-cache` 后缀**（`openlair-backend-cache` / `openlair-web-cache`），与业务镜像 repo 物理隔离。超哥明确不接受 hex tag 出现在业务镜像 repo 下（"不然仓库都是这个玩意了"）。
- 需说明的机制事实：**cache 的 tag 是 buildah 内部按 sha256(cacheKey) 自动生成的，CLI 不可自定义**，能控的只有 repository 名。故"镜像名 + -cache"只能作用于 repo 层（已实现），tag 层无法改成 `:cache` 这种可读形式。
- 若将来要求「Harbor 里连 cache repo 都不出现」，唯一路径是放弃 registry 缓存，改 runner 侧持久化 buildah storage（hostPath/PVC）+ 仅 `--layers`。
